<methodology>

## **Comprehensive Black-Box XSS Vulnerability Analysis (Discovery-to-Execution)**

- **Goal:** Exhaustively discover the application's input points and render surfaces from the outside, map how untrusted sources reach output sinks, and confirm - via live browser execution - which of those paths lack a context-appropriate defense. This approach is optimized for finding all types of XSS: Reflected, Stored, and DOM-based (including mutation XSS).
- **Core Principle:** Data is assumed to be tainted until you **observe** a context-appropriate output encoder or sanitizer neutralize it on its path to the sink. Reflection alone is never proof; execution in a real browser is.

### **1) Seed your target inventory and create a todo per input point/sink (TodoWrite)**
Read `deliverables/recon_deliverable.md` and `deliverables/pre_recon_deliverable.md`. If recon enumerated reflection points, input parameters, or DOM sinks, seed a **TodoWrite** item for each. Regardless of what recon provides, you WILL run your own discovery crawl (Step 2) and add every input point you find. The customer cares most about endpoint-level bugs, so err toward over-enumeration.

### **2) Endpoint, Parameter & Sink Discovery (Discovery-First - be exhaustive)**
Map the full external input surface before probing:
- **Crawl with Playwright** across authenticated and unauthenticated states. Capture every page, form, and client-side route (including hash/history routes).
- **Enumerate every reflection/input point:** URL query params, path segments, the URL fragment (`#...`), request headers an attacker can influence (Referer, User-Agent, X-Forwarded-*, custom headers echoed back), cookies, form fields, JSON/XML request bodies, file upload filenames/content, WebSocket messages, and `postMessage` channels.
- **Enumerate stored-input surfaces** - anything a user can persist that later renders to themselves, to other users, or in an admin/moderation view: comments, profile fields, display names, bios, filenames, support tickets, chat messages, reviews, tags. These are your Stored XSS candidates.
- **Download and statically analyze the served JS bundles + sourcemaps** for DOM sinks and the sources that flow into them (see the sink/source lists in `<available_tools>`), and to recover client-side routing and event handlers. This is your richest DOM-XSS intelligence.

### **3) Map Sources → Sinks in the Served Client-Side Code**
From the downloaded bundles/sourcemaps, trace which DOM sources (`location.hash`/`search`/`href`, `document.referrer`, `window.name`, `postMessage`, storage) reach which DOM sinks, and through which client-side routes and handlers. Record each candidate `source → path → sink` as a todo to confirm live. Where code is minified, delegate deobfuscation and flow-mapping to a Task agent working on the served files.

### **4) Live Detection via Injection + DOM Observation (Execution Oracle)**
For each pending todo, inject a context-appropriate probe and OBSERVE the actual result in the browser - not just the raw reflection:
- Use a unique canary token (e.g., `zqxCANARY123`) to locate exactly where and how your input lands in both the raw response and the rendered DOM.
- Determine the **render context** from what you observe (HTML body, HTML attribute value, inside a `<script>`/JS string, a URL/`href`, or a CSS value).
- Escalate the canary to a minimal breakout probe for that context and confirm **execution** via a real oracle: an `alert`/`prompt` dialog, a `console.log` you injected, a DOM node created by your payload, or an out-of-band callback firing. Reflection without execution is NOT a finding (mark it for context-specific probing or as safe).

### **5) Context-Specific Probing and Stored/DOM Coverage**
- **HTML_BODY:** attempt tag introduction (`<svg onload=...>`, `<img src=x onerror=...>`).
- **HTML_ATTRIBUTE:** attempt attribute/quote breakout and event-handler injection (`" onmouseover=...`).
- **JAVASCRIPT_STRING:** attempt string/expression breakout (`'`, `"`, backtick, `</script>`).
- **URL_PARAM / href:** attempt `javascript:` URI and protocol-relative redirects.
- **CSS_VALUE:** attempt expression/`url()` injection where applicable.
- **Stored XSS:** submit the canary/payload to each storage surface, then **revisit every render location** (your own view, other users' views, lists, admin/moderation panels reachable in scope) and observe whether it executes there.
- **DOM XSS:** drive the specific sink directly - set `location.hash`, post crafted `postMessage` data, set `window.name`, or seed storage - and observe the sink executing your payload.

### **6) Assess Observed Defenses (Dynamic)**
Record the defenses you can actually observe, and whether they hold in the render context:
- **CSP:** capture the `Content-Security-Policy` header (or meta) and its directives. Note `unsafe-inline`/`unsafe-eval`, allowlisted CDNs that may host script gadgets/JSONP, missing `base-uri`, and nonce/hash reuse - all candidate bypass surface for the exploitation phase.
- **Framework auto-escaping:** observe live whether the framework encodes your probe by default, and where developers opted out (e.g., `dangerouslySetInnerHTML`, `v-html`, `[innerHTML]`, `|safe`).
- **Client-side sanitizers:** note any sanitizer (DOMPurify, etc.) visible in the served bundle and its observed configuration/gaps.
- **Cookie flags & WAF:** note HttpOnly/SameSite on session cookies and any WAF behavior that transforms or blocks payloads (a block is an obstacle to bypass, not proof of safety).

### **7) Decide if the Observed Encoding Matches the Sink's Context (Core Rule)**
A path is vulnerable when the defense you observed is absent or wrong for the render context:
- **HTML_BODY:** Requires **HTML Entity Encoding** (`<` → `&lt;`).
- **HTML_ATTRIBUTE:** Requires **Attribute Encoding** (and quoted attributes).
- **JAVASCRIPT_STRING:** Requires **JavaScript String Escaping** (`'` → `\'`) - HTML-entity encoding does NOT help here.
- **URL_PARAM:** Requires **URL Encoding** plus scheme validation (block `javascript:`).
- **CSS_VALUE:** Requires **CSS Hex Encoding**.
- **Mismatch:** If your probe reaches the sink and executes (or would clearly execute) because the observed encoding does not match the context, the path is vulnerable.

### **8) Make the Call, Document, and Score Confidence**
- **Vulnerable:** A full input-point-to-sink path is confirmed with observed execution or an unambiguous encoding mismatch in the render context.
- **Document Finding:** Use the `exploitation_queue_format`. For each vulnerable path, create a separate entry. Every finding MUST be backed by a concrete observed injection→execution transcript: the exact request/URL, the exact payload, and the observed execution evidence. Include both safe and vulnerable paths across your two deliverables to demonstrate **full coverage** (vulnerable → queue; safe → secure table in the report).
- **Witness payload:** craft a minimal `witness_payload` whose execution you actually observed.
- **Confidence:**
    - **High:** Reproducible execution observed live in the browser with a clear render-context mismatch.
    - **Medium:** Reflection lands in an exploitable context and a mismatch is evident, but execution is intermittent or partially filtered (bypass likely).
    - **Low:** Suspicious reflection or a sink pattern seen in served JS, but no confirmed execution yet.
</methodology>


<advanced_topics_to_consider>
- DOM Clobbering: Can you inject HTML with id or name attributes that overwrite global JavaScript variables the served code relies on? (e.g., <input id=config>). Confirm against the behavior you observe in the live app.
- Mutation XSS (mXSS): Does the browser's own HTML parser create a vulnerability when it "corrects" malformed HTML containing your payload after a sanitizer runs? (e.g., <noscript><p title="</noscript><img src=x onerror=alert(1)>">). Test this live against any client-side sanitizer you observed.
- Template Injection: If you observe behavior suggesting a client- or server-side templating engine (e.g., {{ 7*7 }} evaluating to 49 in the response/DOM), probe for template-syntax injection in addition to HTML.
- CSP Bypasses: From the observed Content-Security-Policy, can it be bypassed with JSONP endpoints, script gadgets in allowlisted libraries, base tag injection, or unsafe-inline/eval? Document the concrete bypass surface for the exploitation phase.
</advanced_topics_to_consider>

<false_positives_to_avoid>
- Self-XSS: A vulnerability that requires the user to paste the payload into their own browser. Generally not a finding unless it can be used to trick another user.
- WAF Blocking: A Web Application Firewall (WAF) blocking your payload does not mean the underlying rendering is secure. Document the WAF behavior, but the goal is to find a bypass and report the root cause vulnerability.
- Content-Type Mismatches: An X-Content-Type-Options: nosniff header is a defense against some attacks but does not prevent XSS on its own.
- Incorrect Encoding as a Fix: HTML encoding inside a JavaScript string (var x = '&lt;script&gt;...';) does not prevent XSS, as the browser will not interpret it as a tag in that context. The vulnerability is breaking out of the JS string itself.
- Reflection ≠ Execution: A payload appearing verbatim in a response or the DOM is only a lead. If you could not make it execute in the browser after context-appropriate probing, it is not a confirmed finding.
</false_positives_to_avoid>

## 2. Dominant Vulnerability Patterns

**Pattern 1: Reflected XSS in Search Parameter**
- **Description:** A recurring pattern was observed where the main search parameter (`?q=`) is reflected directly into the HTML body without any output encoding, and a probe executed in the browser.
- **Implication:** Any page with a search bar is likely vulnerable to basic reflected XSS. This is the easiest vector for exploitation.

**Content Security Policy (CSP) Analysis**
- **Observed CSP:** `script-src 'self' https://trusted-cdn.com;` (captured from response headers)
- **Critical Bypass:** The trusted CDN hosts an old version of a library vulnerable to client-side template injection / script gadgets. This provides a clear path to bypass the CSP.
- **Recommendation:** Exploitation should focus on gadget/sandbox-escape payloads hosted by the allowlisted origin.

**Cookie Security**
- **Observation:** The primary session cookie (`sessionid`) is missing the `HttpOnly` flag (observed in Set-Cookie / document.cookie).
