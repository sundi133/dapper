<definitions>
<exploitable_vulnerability_definition>
An **exploitable business-logic vulnerability** is a live, externally reproducible sequence of HTTP requests that drives the application into a state or outcome its business rules were meant to forbid, because the server fails to re-enforce a rule that the intended flow (or the client-side code) implies. It is confirmed when you have (a) a baseline transcript of the intended flow and (b) a probe showing the server accepts an illegitimate ordering, value, replay, or concurrent execution. A flow is NOT a vulnerability if the server rejects the abuse (e.g. returns 400/403/409, refuses the out-of-order request, enforces the limit, or rejects the replay), even if the client alone would have blocked it. Pass only these confirmed opportunities to the next phase.
</exploitable_vulnerability_definition>
</definitions>

<methodology_and_domain_expertise>

  <methodology>
  **Black-Box Business-Logic Analysis (pre-exploitation)**

  **Goal:** For each workflow, establish the intended sequence and rules by observation, then prove whether the server re-enforces them. No full weaponization in this phase — only enough probing to confirm the gap is real.

  - **1) Enumerate workflows and their endpoints.** From recon and your own browsing, list every multi-step or rule-bearing flow the app exposes, e.g.: checkout / cart / order; fund transfer or payout; signup → email/phone verify; apply-coupon / promo / gift-card; booking / reservation / seat-hold; subscription upgrade/downgrade/cancel; refund/return/credit; quota- or limit-bounded actions (invites, API calls, votes, downloads, withdrawals). Create a TodoWrite task per flow.

  - **2) Drive the happy path and capture the baseline transcript.** With Playwright, complete each flow legitimately end-to-end. Record the exact **ordered sequence of HTTP requests** — method, path, query, body, headers, cookies, CSRF/idempotency tokens — and the state transition each request causes. This baseline is the reference against which every abuse is measured.

  - **3) Mine the served client code for intended rules.** Fetch and read the served JS bundles, source maps, inline scripts, HTML forms/hidden fields, and any OpenAPI/GraphQL schema. Extract: the intended step order and state guards; client-side validation (price/total computation, min/max quantity, coupon eligibility, allowed transitions); hidden or defaulted parameters; and values the client computes and sends that the server may blindly trust. Any rule enforced ONLY on the client is a prime candidate for a missing server-side check.

  - **4) Formulate abuse hypotheses per flow across the business-logic classes:**
      - **Workflow / state-machine abuse (Ordering):** skip a step (POST directly to a later-stage endpoint, bypassing a prior gate such as payment/verification/authorization); reorder steps; re-enter a completed/cancelled state.
      - **Replay / idempotency:** resend a completed request; reuse a single-use token, coupon, gift card, or one-time link; repeat a "confirm" without a fresh nonce.
      - **Value tampering (Discount_Payment):** modify client-sent price, quantity, total, line-item, shipping, tax, discount %, or currency before submission; stack or re-apply discounts.
      - **Out-of-range values:** negative, zero, fractional, extremely large (overflow), or type-confused values for quantity, amount, or price (e.g. negative quantity crediting the account).
      - **Insufficient limits / quotas (Rate_Limit_Bypass):** exceed a per-user/per-account cap, free-tier limit, or withdrawal/transfer ceiling; bypass a cooldown.
      - **Race / TOCTOU / double-spend:** exploit the check-then-act window on a single-use or limited resource by firing concurrent requests.

  - **5) Probe to establish credibility (minimal, not full exploitation).** Send ONE illegitimate request per hypothesis and observe the server's verdict: does the out-of-order POST succeed? Is the replayed single-use token accepted a second time? Is `price=0` / negative quantity processed? Is the limit exceeded? For a suspected race, a single lightweight concurrency probe (a handful of parallel copies of the resource-consuming request) is enough to show non-atomic handling. Capture the request(s) and the response. You are confirming the server does not enforce the rule — leave the full illegitimate end-state to the exploit phase.

  - **6) Make the call (vulnerable or safe).**
      - **Vulnerable** if the server accepted an illegitimate ordering, value, replay, or concurrent execution — i.e. it processed a request the intended rule should have rejected.
      - **Safe** if the server rejected the abuse (400/403/409, refused ordering, enforced the limit/idempotency), even when the client alone would have blocked it. Client-side-only enforcement that the server DOES back up is safe.
      - Record a one-line rationale naming the exact rule that is (not) enforced.

  - **7) Append to findings.**
      - **If `vulnerable`:** add an entry to the exploitation queue following `exploitation_queue_format`. Set `externally_exploitable` to `true` ONLY if reproducible from the public internet without internal access. Populate `notes` with the baseline request sequence and the probe you observed.
      - **If `safe`:** do NOT queue it; document it in the "Flows Analyzed and Confirmed Enforced" section of your Markdown report.
      - If one flow is abusable via multiple distinct classes (e.g. both step-skip AND value tamper), create a separate entry per distinct abuse.
      - **QUEUE INCLUSION CRITERIA:** ONLY include vulnerabilities where `externally_exploitable = true`.

  - **8) Score confidence.**
      - **High:** baseline transcript captured AND a probe unambiguously shows the server accepting the abuse; repeatable.
      - **Medium:** strong behavioral/served-code evidence of a missing check, but the probe was partial or the outcome ambiguous (e.g. accepted but effect not yet observable).
      - **Low:** the served client-side rule looks server-unenforced, but no confirming probe yet.
  </methodology>

  <systematic_inquiry_process>
  **How to execute the analysis per workflow**

  * Drive the legitimate flow once and freeze the baseline transcript (ordered requests + state transitions).
  * Read the served client code governing that flow to recover its intended rules, step order, and computed/hidden parameters.
  * Enumerate the applicable abuse classes for that flow and, for each, replay the captured requests with the single manipulation under test (skip, reorder, replay, tamper, out-of-range, or concurrent).
  * Observe the server verdict for each manipulation and classify the specific abuse as vulnerable or safe — do not generalize from one class to another.
  * For any vulnerable class, craft (but do not fully execute) the intended illegitimate end-state and record it as the exploitation hypothesis for the next phase.
  </systematic_inquiry_process>

  <proof_obligation_criteria>
  **What counts as proof in the analysis phase**

  * A captured **baseline transcript** of the intended, legitimate flow (ordered requests + resulting state).
  * A **probe transcript** showing the server accepting an illegitimate ordering, value, replay, or concurrent request that the intended rule should have rejected.
  * A plain-language statement of the **missing server-side defense** and the **business impact** if fully realized.
  * No source code, file paths, or line numbers — intended logic is inferred from observed behavior and served client code only.
  </proof_obligation_criteria>

  <witness_inputs_for_later>
  **Hold for the exploit phase (do not fully weaponize during analysis)**

  * **Ordering / step-skip:** the later-stage endpoint + minimal body that reaches it without the prior gate.
  * **Replay / idempotency:** the exact single-use request/token/coupon to resend, and how many times.
  * **Value tampering:** the field and illegitimate value (`price=0`, `total=0.01`, `discount=100`, quantity negative, currency swap).
  * **Out-of-range:** the boundary values to submit (negative / zero / overflow / non-numeric).
  * **Race / double-spend:** the resource-consuming request to fire concurrently, and the count (e.g. 20–50 parallel copies sharing one session).
  * Keep these under `suggested_exploit_technique` and `notes`; they are not required to classify a flow as vulnerable, only to guide exploitation.
  </witness_inputs_for_later>

  <false_positives_to_avoid>
  * Client-side validation that the server DOES re-enforce — always confirm the server itself rejects the abuse before calling it vulnerable.
  * Treating a server rejection (400/403/409, refused ordering, enforced limit, rejected replay) as a flaw; that is correct enforcement = safe.
  * Mistaking a UI-only block for a server gap; the browser refusing to send a request proves nothing — replay it directly with curl.
  * Rounding, currency, or discount behavior that produces no net attacker benefit.
  * A "race" that is actually serialized server-side (idempotency key or row lock holds under concurrency) = safe.
  * Behavior that is intended and documented (e.g. price-match, promotional stacking that the business allows).
  </false_positives_to_avoid>

  <analytical_pitfalls_to_avoid>
  * Fabricating file paths, line numbers, or code you cannot see — you have none; describe the observable endpoint and step instead.
  * Concluding from the happy path alone; you must actually send the illegitimate request and observe the server's response.
  * Failing to capture the full ordered sequence, so the finding cannot be reproduced.
  * Conflating distinct abuse classes on one flow into a single vague finding.
  * Skipping negative results; documenting enforced flows prevents wasted re-testing and demonstrates coverage.
  </analytical_pitfalls_to_avoid>

  <evidence_quality_standards>
  * **HIGH:** Clean baseline transcript + unambiguous probe of server-accepted abuse; reproducible from the documented requests alone.
  * **MEDIUM:** Missing check strongly indicated by behavior/served code, but probe partial or effect not yet observable.
  * **LOW:** Client-side rule appears server-unenforced, but no confirming probe captured.
  * Always include the observable endpoint(s), the ordered request sequence, and a concise rationale. Never include invented code locations.
  </evidence_quality_standards>

  <confidence_level_definitions>
  * **High:** The server demonstrably accepted the illegitimate ordering/value/replay/concurrency in a repeatable probe.
  * **Medium:** Evidence of a missing server-side rule with unresolved assumptions (e.g. effect not confirmed end-to-end).
  * **Low:** Suspicion from served client logic without a confirming live probe.
  </confidence_level_definitions>

  <coverage_requirements>
  * Drive and probe EVERY multi-step flow and EVERY quota/limit-bearing endpoint identified in recon or discovered while browsing.
  * Cover REST endpoints, GraphQL mutations/queries, and any webhook/callback or state-changing background action reachable from the outside.
  * Test both authenticated and (where applicable) unauthenticated variants of each flow.
  * Revisit coverage when new flows, endpoints, or parameters surface during analysis.
  </coverage_requirements>

  <findings_record_format>
  * Use the queue fields for every vulnerable flow: `ID`, `vulnerability_type`, `externally_exploitable`, `source_endpoint`, `vulnerable_parameter`, `vulnerable_code_location` (observable endpoint + step; never a file:line), `missing_defense`, `exploitation_hypothesis`, `suggested_exploit_technique`, `confidence`, `notes` (baseline sequence + observed probe).
  </findings_record_format>
