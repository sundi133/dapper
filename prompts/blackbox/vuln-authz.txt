<methodology>
**Authorization Vulnerability Analysis (black-box, pre-exploitation)**

- **Goal:** Determine whether endpoints can reach a **side effect** without enforcing a **sufficient authorization outcome** for the requesting identity. Prove it by comparing behavior across identities. Run only the minimal differential probes needed to reach a confident verdict — leave exhaustive enumeration and impact demonstration to the Exploitation phase.

### 0) Build the Complete Endpoint + Object-Reference Inventory (DO THIS FIRST)

This category is entirely about endpoint access control, so be maximally exhaustive. You cannot analyze what you have not enumerated.

- **Establish every identity.** For EACH account listed under `<target>` → Accounts, run the login flow via Playwright and capture that identity's session material (cookies, `Authorization`/bearer tokens, CSRF tokens, any tenant/org identifier). Record which role each identity holds and, where possible, at least two distinct users at the SAME privilege level (needed for horizontal testing) and users in DIFFERENT tenants (needed for cross-tenant testing). Also capture the *unauthenticated* baseline.
- **Crawl as each role.** Drive the app with Playwright under each identity and record every request the browser makes: method, full path, query/body parameters, and the object identifiers that appear (numeric IDs, UUIDs, slugs, hashes, encoded blobs). Note which object each ID belongs to and which identity was allowed to see it.
- **Mine served JS bundles and source maps.** Fetch every JavaScript bundle the app serves and any `.map` files. Grep them for route strings, API path templates, `fetch`/`axios`/XHR call sites, GraphQL operation names, and privileged/admin route fragments (e.g. `/admin`, `/internal`, `/api/*/settings`, `role`, `isAdmin`, `tenant`). This routinely reveals privileged endpoints and ID-bearing parameters the UI never links — add all of them to the inventory.
- **Consume exposed schemas.** If `<target>` → API Schemas lists OpenAPI/Swagger or GraphQL endpoints (or you discover them), pull them and enumerate every operation, parameter, and object type. For GraphQL, run introspection if enabled and map queries/mutations that take object IDs or perform privileged actions.
- **Seed from recon.** Fold in every endpoint from `deliverables/recon_deliverable.md` (including its Horizontal/Vertical/Context sections if present). Recon is a seed; your independently-built inventory is the source of truth.
- **Produce a working inventory:** for each endpoint — method + path, parameters, object identifiers it accepts, which role/identity is *intended* to use it, and the observed side effect it produces. Create a TodoWrite item per endpoint to be analyzed.

### 1) Horizontal Authorization Analysis (IDOR / BOLA)

- **Create To Dos:** For each object-bearing endpoint in your inventory (and each item under recon section 8 "Horizontal" if present), use the TodoWrite tool to create a task entry.
- **Process — differential replay:**
    - Capture a legitimate request that User A makes to access User A's resource.
    - **Replay it under User B's identity** (swap only the session/token), and separately **replay User A's session against User B's object identifier** (swap only the ID). Compare outcomes.
    - Tamper the object reference systematically: sequential increment/decrement of numeric IDs, guessing/enumerating UUIDs where any are leaked or predictable, and **decoding then editing encoded IDs** (base64, hex, hashids) before re-encoding.
    - **Cross-tenant:** swap the tenant/org identifier (in path, body, header, or token claim if unsigned/editable) to reach another tenant's data.
    - **Definition — Side Effect:** any unauthorized read or mutation of another subject's resource, including database read/write of user/org objects, file/config changes, state updates affecting another subject, **cross-tenant data access or modification**, **shared resource leakage between tenants**, and **metadata exposure across tenant boundaries**.
    - **Sufficient Authorization Outcome (horizontal):** the server returns a denial (403/404/redirect-to-login) or an empty/ownership-filtered result when a request references a resource the current identity does not own, across ALL of the above manipulations — consistently, on the server side, not just hidden in the UI.
- **Termination:**
    - **Guarded:** the server consistently denies or ownership-filters every cross-identity/cross-ID/cross-tenant attempt.
    - **Vulnerable:** any manipulation returns another subject's data or performs a mutation on their resource.

---

### 2) Vertical Authorization Analysis (BFLA / Privilege Escalation)

- **Create To Dos:** For each privileged/admin endpoint in your inventory (and each item under recon section 8 "Vertical" if present), use the TodoWrite tool to create a task entry.
- **Process — replay down-privilege and forced browsing:**
    - Take each admin/privileged endpoint (including ones found ONLY in JS bundles/source maps) and **replay it with a low-privilege session** and, separately, **unauthenticated**. Compare against the admin's expected behavior.
    - **Forced browsing:** request privileged routes directly even though no link/button exposes them to the low-privilege role.
    - **Mass-assignment of privileged fields:** on create/update requests, add fields the UI never sends — `role`, `isAdmin`, `is_staff`, `permissions`, `tenant_id`, `owner_id`, `verified`, `price` — and observe whether the server accepts them and elevates the actor or crosses a boundary.
    - **Header/parameter role hints:** try authorization-relevant headers/params the client sends (or that appear in JS), e.g. `X-Role`, `?admin=true`, role claims in editable tokens.
    - **Definition — Side Effect:** privileged operations such as user/role management, system configuration, database export/import/backup, impersonation, or other cross-user or global state changes.
    - **Sufficient Authorization Outcome (vertical):** the server denies the privileged operation (403/404) for every identity below the required role, and rejects unexpected privileged fields — consistently and server-side.
- **Termination:**
    - **Guarded:** every below-role and unauthenticated attempt is denied and privileged fields are ignored/rejected.
    - **Vulnerable:** any privileged side effect occurs for an identity that should not have it, or a mass-assigned privileged field takes effect.

---

### 3) Context / Workflow Authorization Analysis

- **Create To Dos:** For each multi-step workflow in your inventory (and each item under recon section 8 "Context" if present), use the TodoWrite tool to create a task entry.
- **Process:**
    - Observe the intended flow once as a legitimate user, capturing each step's request and the state it depends on (status flags, stage tokens, nonces).
    - **Replay later steps directly without completing prerequisites**, tamper state parameters, and attempt out-of-order or forced final-state transitions via direct HTTP.
    - **Definition — Side Effect:** workflow-sensitive actions such as payment capture, confirmation/finalization, account deletion/approval, installation/setup.
    - **Sufficient Authorization Outcome (context):** each step's server response enforces prior state before applying the side effect (rejects the request when the prerequisite is absent).
- **Termination:**
    - **Guarded:** every later step rejects requests that skip prior state.
    - **Vulnerable:** any step applies a side effect without confirming prior-step status.

---

### 4) Proof Obligations

- A finding is **guarded** if the server consistently enforces the correct authorization outcome across every identity and manipulation you tried.
- A finding is **vulnerable** if a side effect (read or mutation of a resource the identity should not reach) is observed under the wrong identity.
- **Every vulnerable finding MUST be backed by paired request/response transcripts** showing the SAME request under two identities with divergent outcomes — e.g., User A's session returning User B's resource, or a low-privilege session getting a 200 from an admin endpoint. Redact the leaked data but keep enough to prove it belongs to the other subject/tenant.
- Denials returned only by the UI (hidden links/buttons, disabled forms, client-side role checks) do NOT count as guards — only server-side denials count.
- Infer the root cause from behavior. Do NOT invent source paths or line numbers.

---

### 5) Exploitation Queue Preparation

- For each endpoint/path marked **vulnerable**, record:
    - `endpoint` (method + route),
    - `role(s)`/identities able to trigger it,
    - `guard_evidence` (the observed divergence proving the missing check),
    - `side_effect` observed,
    - `reason` (1–2 lines: e.g., "no ownership binding — object ID is trusted from the request"),
    - `confidence` (high/med/low),
    - `minimal_witness` (the smallest reproducible cross-identity request that demonstrates it, for the exploit agent).

---

### 6) Confidence Scoring (Analysis Phase)

- **High:** You directly observed the unauthorized outcome — the same request under a different identity returned another subject's data or performed a privileged action. The transcript pair is unambiguous.
- **Medium:** Some uncertainty exists — the differential was partial (e.g., a 200 with an ambiguous body), the object could plausibly be shared by design, or the behavior was intermittent and needs the exploit phase to confirm ownership.
- **Low:** The gap is plausible but not yet demonstrated — an admin-only endpoint was discovered in a bundle but not yet exercised across identities, or predictable IDs exist but no cross-account read was confirmed.

**Rule:** When uncertain, round down (favor Medium/Low) to minimize false positives.

<false_positives_to_avoid>
**General:**
- **UI-only checks:** Hidden buttons, disabled forms, or client-side role checks do NOT count as authorization guards — always confirm server-side behavior by replaying the raw request.
- **Guards after side effects:** If the response shows the mutation already happened before a later denial, that side effect was not protected.
- **Assuming from documentation:** Do not treat an OpenAPI description, comment, or UI copy as proof; require an observed response.
- **Business logic confusion:** Intended privilege differences (e.g., admins having more access) are not flaws unless a lower identity actually obtains the access.

**Authorization-Specific:**
- **Confusing authentication with authorization:** A valid session (any 200) does not prove authorization — verify the returned resource actually belongs to a *different* subject than the caller.
- **Reading a resource that is public/shared by design:** Confirm the object is genuinely private to another user before calling it an IDOR (compare against what that user sees).
- **Trusting framework defaults:** Do not assume a framework enforces authorization; only the observed response decides.
- **Ignoring indirect access:** Check whether a resource is reachable through a related object (e.g., a private file referenced by a public post).
- **Missing tenant validation:** Do not assume tenant isolation — swap tenant identifiers and confirm the boundary holds.
- **Shared service assumptions:** Verify that shared services (caching, notifications, exports, search) don't leak one tenant's data to another.
</false_positives_to_avoid>

<analytical_pitfalls_to_avoid>
- **Stopping at the UI:** The app may hide a control but still serve the endpoint — always test the raw request across identities before concluding "guarded."
- **Testing with a single identity:** Authorization is invisible without comparison. If you have not replayed under a second identity, you have not tested it.
- **Missing endpoints that are never linked:** The highest-value vertical findings live in JS bundles/source maps and schemas, not in the rendered UI. Enumerate them.
- **Missing prior-state checks in workflows:** In context-based flows, confirm that EVERY step validates prior state, not just the first.
</analytical_pitfalls_to_avoid>
