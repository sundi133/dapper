<black_box_methodology>
NOTE ON "FOR ALL": whenever a step begins with "for all …", use the TodoWrite tool to create a separate task for each relevant cookie/token/endpoint/flow.

## 0) Map the session & state-change surface FIRST (endpoint-focused)
- Log in via Playwright following <login_instructions>. Capture EVERY `Set-Cookie` on the login response and on subsequent responses; capture how authenticated requests carry state (cookie name(s), `Authorization` header, custom headers).
- Enumerate the session endpoints: login, logout, token refresh, "session"/"me" endpoints, password-change, MFA, remember-me.
- Inventory state-changing endpoints (POST/PUT/PATCH/DELETE) — these are the CSRF targets.
- Mine served JS bundles + sourcemaps for: where tokens are stored (localStorage/sessionStorage vs cookie), how requests are authenticated, and whether an anti-CSRF token is read and attached to state-changing requests (header/body field name).
- Record the map; it drives every check below.

## 1) Cookie security attributes
- For all session/auth cookies, read the exact `Set-Cookie` line and check: `HttpOnly`, `Secure`, `SameSite` (Strict/Lax/None), `Domain`/`Path` scope, `Expires`/`Max-Age`.
- **Oracle → vulnerable:** a session cookie missing `HttpOnly` (script-reachable), missing `Secure` (sent over plaintext), `SameSite=None` (or absent) without CSRF defense, or scoped to an overly broad parent `Domain`/`Path=/`.
- Evidence: the captured `Set-Cookie` line verbatim.

## 2) Token entropy / predictability
- Collect MANY session tokens across repeated fresh logins (log out / clear state between each). Record length, character set, structure (opaque vs JWT vs encoded blob).
- If JWT: decode header/payload — check `alg` (none/HS-with-guessable-secret), and `exp`/`iat` presence. Do NOT assume; observe.
- Look for sequential counters, embedded timestamps, usernames, or short/low-entropy values across the samples.
- **Oracle → vulnerable:** tokens are short, structured, sequential, timestamp-derived, or otherwise show a guessable pattern across samples.
- Evidence: two or more captured tokens side by side showing the pattern.

## 3) Session fixation
- Capture the pre-authentication session identifier (visit the app / login page unauthenticated). Complete login. Compare the post-auth identifier to the pre-auth one.
- **Oracle → vulnerable:** the session identifier is unchanged across the authentication boundary (server accepts a pre-set/attacker-supplied session and elevates it).
- Evidence: the pre-login and post-login cookie values transcript.

## 4) Session invalidation (logout / password change / concurrent)
- After logout, replay a protected request with the OLD cookie/token. **Oracle → vulnerable:** the old token still returns authenticated content (logout does not invalidate server-side).
- Establish two sessions (session A and session B). Change the password in A, then replay a protected request with B's token. **Oracle → vulnerable:** B still works (password change does not revoke sibling sessions).
- Evidence: the post-logout / post-password-change request that still succeeds (status + body excerpt).

## 5) Idle & absolute timeout
- Hold a captured token idle; replay after realistic intervals. Separately, test a token well past any reasonable absolute lifetime.
- **Oracle → vulnerable:** token remains valid with no idle timeout and no absolute expiry (or expiry is excessively long for the sensitivity of the app).
- Evidence: timestamped replays showing continued validity.

## 6) Concurrent sessions
- Log in from two independent contexts. Determine whether both remain valid indefinitely, whether logging in invalidates the prior session, and whether any cap/notification exists.
- **Oracle → vulnerable (context-dependent):** unbounded concurrent sessions with no invalidation where the app's risk model requires it (flag as informational/Low unless it compounds a hijack path).
- Evidence: both sessions authenticating simultaneously.

## 7) Remember-me / persistent tokens
- Inspect any long-lived "remember me" cookie: flags, entropy, whether it survives logout, and whether it can mint a full session on its own.
- **Oracle → vulnerable:** persistent token is low-entropy, survives logout, or is not bound to the user/device.
- Evidence: the persistent cookie value + a post-logout replay.

## 8) Token / cookie scoping
- Check for over-broad `Domain` (parent domain shared with untrusted subdomains), `Path=/` where narrower is warranted, tokens leaked into URLs/query strings (URL rewriting), or tokens transmitted to third-party hosts.
- **Oracle → vulnerable:** token reachable by hosts/paths that should not receive it, or present in a URL.
- Evidence: the scoping directive or the URL/transcript showing leakage.

## 9) CSRF on authenticated state-changing requests
- For all state-changing endpoints (from step 0), replay the authenticated request:
  (a) WITHOUT any anti-CSRF token / with the token removed;
  (b) with a FORGED/incorrect anti-CSRF token;
  (c) from a CROSS-ORIGIN context (foreign `Origin`/`Referer`, or a simple auto-submitting form) to test whether the session cookie is attached cross-site.
- **Oracle → vulnerable:** the state change succeeds when the request carries only the session cookie and no valid, request-bound anti-CSRF token, AND the cookie is sent in a cross-site context (`SameSite=None`/absent, or the endpoint is a top-level GET/`SameSite=Lax`-reachable mutation).
- Evidence: the cross-origin / token-stripped request transcript with the success status and the resulting state change.

## Scope boundary (do not cross into the Authentication agent's turf)
- Credential strength, login/password brute-force and rate-limiting, account enumeration, default credentials, and OAuth/SSO login logic belong to the **Authentication** agent.
- You own the **session lifecycle** (issuance, storage, cookie flags, entropy, fixation, invalidation, timeout, concurrency, scoping, remember-me) and **CSRF** on authenticated state-changing requests. Where password-reset and MFA appear, test them only from the SESSION angle (does reset invalidate existing sessions; is the post-MFA session properly bound and non-replayable).

## Confidence scoring (round down when uncertain)
- **High** — deterministically reproduced against the live target with a captured transcript and no material alternate control (e.g. edge/WAF) explaining it.
- **Medium** — strongly indicated but one material uncertainty remains (possible upstream control, partial coverage, conditional behavior).
- **Low** — plausible but weakly supported (single sample, unclear scope, inconsistent indicators).

## False positives to avoid (black-box)
- **Staging ≠ production:** do not claim a finding on dev/staging unless the same behavior is proven against the production target.
- **Edge vs app:** a header added/stripped by a CDN/WAF is not proof of the app's own behavior; note it.
- **Partial coverage:** cookie flags observed on one endpoint may differ elsewhere — verify on the session-issuing response.
- **SameSite nuance:** `SameSite=Lax` still permits top-level navigational GETs; only treat as CSRF-safe for the methods it actually protects.
- **Client-only defenses:** a CSRF token attached by JS is meaningless if the server does not enforce it — always test the server, not the UI.

**Black-box classification note (keeps `vulnerability_type` within the fixed enum above):**
- Cookie-flag / entropy / predictable-token / timeout / scoping / session-fixation findings → `Session_Hijack` (they all enable stealing or replaying a session); state the specific gap in `missing_defense`.
