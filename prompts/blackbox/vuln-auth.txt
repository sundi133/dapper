<methodology>
# Black-Box Vulnerability Analysis Procedure: Broken Authentication (AuthN-only)

NOTE ON "FOR ALL": whenever an item begins with "for all …", use the TodoWrite tool to create a separate task for each relevant endpoint/flow that needs to be analyzed.
From `deliverables/pre_recon_deliverable.md` and `deliverables/recon_deliverable.md`, use the reconnaissance sections to seed your tasks, then extend them with what you discover in Step 0.

## 0) Discover the full auth attack surface FIRST (endpoint-centric)
The customer cares most about endpoint bugs, so map the endpoints before you test anything.
- **Crawl the UI with Playwright:** walk every unauthenticated and authenticated path you can reach — login, logout, "sign up", "forgot password", "reset password", "resend code", MFA/2FA challenge, "sign in with <provider>", account settings. Capture the network traffic behind each action.
- **Capture the network:** for every auth action, record the exact request (method, URL, headers, cookies, body) and the exact response (status, `Set-Cookie`, cache headers, body). This transcript is your evidence.
- **Mine served JS bundles & sourcemaps:** fetch the app's JavaScript and any `.map` files. Extract auth route strings (e.g. `/api/auth/login`, `/api/token/refresh`, `/oauth/callback`), request/response shapes, token field names, client-side validation rules, and any feature flags. Client-side validation reveals what the server might NOT enforce.
- **Check exposed descriptors:** `robots.txt`, `sitemap.xml`, `/.well-known/openid-configuration`, `/.well-known/`, `swagger.json`/`openapi.json`, GraphQL introspection — anything that enumerates auth endpoints or OIDC parameters.
- **Build the inventory:** produce a TodoWrite task per discovered auth endpoint (login, logout, register, password-reset request, password-reset confirm, token refresh, MFA challenge, OAuth authorize/callback, session/whoami). For each, note the parameters and the exact observed request/response so later checks reference real behavior.

## 1) Transport & caching
- For all auth endpoints, confirm HTTPS is enforced (no HTTP fallback/hops; test an `http://` request and observe whether it is refused or redirected before any credential is accepted); check for `Strict-Transport-Security` at the edge. (for all: use TodoWrite tool to add each endpoint as a task)
- For all auth responses (login, reset, token), check `Cache-Control: no-store` / `Pragma: no-cache` so credentials/tokens are not cached by intermediaries.
**Oracle:** the response headers you captured. **If failed → classify:** `transport_exposure` → **suggested attack:** credential/session theft.

## 2) Rate limiting / lockout / monitoring
- For login, signup, reset/recovery, MFA, and token endpoints, send a controlled burst of requests (bounded — enough to reveal the control, not to cause harm) and observe whether per-IP and/or per-account throttling, `429`, `Retry-After`, backoff, CAPTCHA, or account lockout appears.
- For repeated failed logins against one account, observe whether lockout/backoff triggers.
**Oracle:** status codes and timing across the burst (all `200/401` with no slowdown = no limit). **If failed → classify:** `abuse_defenses_missing` → **suggested attack:** brute_force_login / credential_stuffing / password_spraying.

## 3) Session management (cookies)
- For all session cookies (read the `Set-Cookie` you captured at login), check `HttpOnly` and `Secure` flags and an appropriate `SameSite` (typically Lax/Strict).
- After successful login, compare the session identifier before and after auth: verify the session ID is ROTATED (a new value), not reused.
- Ensure logout invalidates the server-side session: capture a valid session cookie, log out, then replay the SAME cookie against an authenticated endpoint — it must now be rejected.
- Probe for idle and absolute session timeout where feasible.
- Confirm session IDs/tokens are transported in cookies, not in URLs/query strings (no session in the address bar or `Referer`).
**Oracle:** captured `Set-Cookie` flags and the replay result. **If failed → classify:** `session_cookie_misconfig` → **suggested attack:** session_hijacking / session_fixation / token_replay.

## 4) Token/session properties (entropy, protection, expiration & invalidation)
- For any bearer token or session ID you can capture, inspect its structure: is it a JWT, an opaque random string, or something guessable/sequential/base64-of-user-data? Request two tokens and compare for predictable structure or low entropy.
- **JWT-specific (decode the header and payload of a captured token):**
  - `alg:none` — forge a header `{"alg":"none"}` with an empty signature and replay against an authenticated endpoint; acceptance means unsigned tokens are honored.
  - Weak/guessable HMAC secret — attempt an OFFLINE dictionary/brute crack of the signature (Task Agent, e.g. hashcat mode 16500) against a captured token; a cracked secret means an attacker can mint arbitrary tokens.
  - Missing/absent `exp` (or an implausibly long lifetime) — decode the claims and note the TTL.
  - `kid` / `jku` / `x5u` header tricks — note if the header references an attacker-influenceable key source.
- Confirm tokens are only sent over HTTPS and are not exposed in URLs or logs you can observe.
- Verify tokens/sessions carry explicit expiration and are invalidated on logout (replay-after-logout test from Step 3).
**Oracle:** the decoded token plus the replay/crack result. **If failed → classify:** `token_management_issue` → **suggested attack:** token_replay / offline_guessing / jwt_alg_confusion.

## 5) Session fixation
- For the login flow, capture the pre-login session identifier (set on first visit), authenticate, then capture the post-login identifier. A secure app issues a NEW identifier on auth success; if the pre-login ID survives authentication, the flow is fixation-prone.
**Oracle:** pre- vs post-login session ID comparison. **If failed → classify:** `login_flow_logic` → **suggested attack:** session_fixation.

## 6) Password & account policy
- Probe the registration/password-change endpoints (where reachable) with weak/common passwords (e.g. `password`, `123456`) and observe whether the server accepts them — server-side rejection is what matters, not the client-side strength meter.
- Look for default/seed credentials hinted by served artifacts, docs, or error text; test only credentials that are in-scope and provided/observed, never real third-party accounts.
- Observe whether MFA is available/enforced where the flow implies it should be.
**Oracle:** the accept/reject response to a weak-password submission. **If failed → classify:** `weak_credentials` → **suggested attack:** credential_stuffing / password_spraying (include observed policy details).

## 7) Login/signup responses (user enumeration & minimal logic checks)
- Compare responses for a KNOWN-valid username vs a KNOWN-invalid username on login, signup, and password-reset-request. Look for differential signals: different error text ("no such user" vs "wrong password"), different status code, different response length, or a measurable timing difference (valid users hashed, invalid users short-circuited). Any reliable differential is username enumeration.
- Ensure auth state is not reflected into URLs/redirects that could be abused (open-redirect via `returnUrl`/`next`).
**Oracle:** the differential across the two response transcripts (and timing). **If failed → classify:** `login_flow_logic` → **suggested attack:** account_enumeration / open_redirect_chain.

## 8) Recovery & logout
- For password reset/recovery: trigger the flow for a controlled account and inspect the token delivered — is it returned in-band in the HTTP/JSON response (it must not be), is it short and predictable (e.g. derived from `Date.now()`, a counter, or base64 of the email), is it single-use and short-TTL, is the endpoint rate-limited, and does the request response leak whether the account exists?
- For logout, verify server-side invalidation and client cookie clearing (replay-after-logout test).
**Oracle:** the reset token's structure/delivery and the reset-request response. **If failed → classify:** `reset_recovery_flaw` → **suggested attack:** reset_token_guessing / reset_token_leak / takeover.

## 9) SSO/OAuth/OIDC (if applicable)
Observe the live redirect flow (Playwright network capture of the authorize request and the callback).
- Validate that `state` (CSRF) and `nonce` (replay) are present, unpredictable, and actually checked — try replaying the callback with a tampered/missing `state`.
- Test `redirect_uri` handling: attempt a modified `redirect_uri` (subpath, different host, open-redirect trick) and see whether the authorize endpoint accepts it instead of enforcing an exact allowlist.
- For issued IdP/ID tokens you can capture, decode and check `alg` (see Step 4), and whether basic claims (`iss`, `aud`, `exp`) look enforced.
- For public clients, observe whether PKCE (`code_challenge`) is used.
- nOAuth-style check: from the ID token/userinfo you can observe, note whether identity appears keyed to a MUTABLE claim (`email`, `preferred_username`, `name`) rather than the immutable `sub`. If mutable, an attacker who controls those attributes at their own IdP tenant may impersonate a victim.
**Oracle:** the captured authorize/callback transcripts and decoded token. **If failed → classify:** `login_flow_logic` or `token_management_issue` → **suggested attack:** oauth_redirect_uri_hijack / state_replay / token_replay / noauth_attribute_hijack.

# Confidence scoring (analysis phase; applies to all checks above)
- **High** — The flaw is directly established and deterministic in the target context. You have a captured transcript (a single safe probe that shows the condition — e.g. the un-rotated ID, the accepted `alg:none` token, the burst with no throttle) with no material alternate control. Scope is clear (which endpoints/flows).
- **Medium** — The flaw is strongly indicated but there is at least one material uncertainty (e.g., a possible upstream control like a WAF you could not conclusively rule out, conditional behavior, or partial coverage). Signals are mostly consistent but a reasonable alternative explanation remains.
- **Low** — The flaw is plausible but unverified or weakly supported (indirect or single-sourced evidence, no reproduction in the target context, unclear scope, or inconsistent indicators).

Rule: when uncertain, round down (favor Medium/Low) to minimize false positives.

<false_positives_to_avoid>
- **Counting client-side mitigations:** Do not consider client-only checks (e.g., a JS strength meter, UI-disguised errors, front-end throttling) as defenses; only server-side enforcement — proven by the response to a direct request that bypasses the UI — counts.
- **Assuming from artifacts:** Do not treat a route string in a JS bundle, a policy comment, or an OpenAPI description as proof of a flaw OR of a defense; confirm with an actual request/response against {{WEB_URL}}.
- **Over-testing:** Do not run destructive brute force or full account takeover here; limit to minimal, bounded safe probes and header/behavior inspection. Weaponization belongs to the Exploitation phase.
- **WAF/edge ambiguity:** A single blocked probe may be an edge control rather than app-level security; note the uncertainty and round confidence down rather than over-claiming.
- **Non-AuthN controls:** Do not mark missing CSP/CSRF (except OAuth `state`/`nonce`) or general content-security items as Broken Authentication.
</false_positives_to_avoid>
